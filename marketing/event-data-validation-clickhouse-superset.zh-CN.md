# 埋点数据写入 ClickHouse 后，如何证明它真的可用？

接口返回 HTTP 200，只能证明请求到达过某个服务，不能证明埋点已经正确进入分析链路。字段类型可能变化，客户端时间可能被错误转换，重试可能制造重复，登录前后的身份也可能被拆成两个用户。

更可靠的验收方法是逐层验证：接收响应、ClickHouse 原始记录、字段语义、聚合 SQL，以及 Superset 看板结果。

> **直接答案：**埋点迁移至少要完成三层核对：确认接收服务日志，使用唯一标记在 ClickHouse 找到原始事件，再用相同口径在 Superset 重现指标。只有三层一致，事件才真正具备分析价值。

## 1. 先发送一条可以唯一定位的测试事件

不要一开始就在海量生产数据里搜索。发送名为 `integration_test` 的事件，并加入测试批次、环境、平台、SDK 版本和合成用户 ID。测试属性应覆盖字符串、整数、布尔值和带时区的时间。

发送前保留原始载荷，它就是后续逐字段比较的预期结果。测试不需要真实个人信息时，应使用合成标识。

## 2. 接收层要验证什么

保存 HTTP 状态、响应正文、请求时间、目标地址和请求 ID，再到服务日志中查找同一批次。需要确认请求进入了正确环境、协议被成功解析、存储操作已经完成，而不是只进入重试队列。

解析警告不能直接忽略。顶层事件即使入库，某个关键属性被静默丢弃，仍然属于数据错误。

## 3. 在 ClickHouse 查原始事件

下面是最小查询示例，实际表名和字段应以部署版本为准：

```sql
SELECT event, distinct_id, event_time, received_at, properties
FROM sensors.event
WHERE event = 'integration_test'
  AND properties['validation_run'] = '2026-09-17-a'
ORDER BY received_at DESC
LIMIT 10;
```

查不到记录，说明问题位于接收到存储之间；出现多条记录，则要判断是否发生重试，以及系统采用什么去重策略。

找到记录后继续核对：

- 事件名的大小写与命名是否一致；
- 匿名 ID、登录 ID 和设备 ID 是否符合身份模型；
- 客户端发生时间与服务端接收时间是否分别保存；
- 数字、布尔、日期和字符串类型是否保持不变；
- 测试环境与生产环境能否明确区分。

ClickHouse 的排序键、分区和常用过滤条件会影响查询读取量。表设计应参考 [ClickHouse 官方文档](https://clickhouse.com/docs)，不能只根据演示数据判断生产性能。

## 4. 用确定批次验证聚合结果

单条事件正确后，发送一个结果已知的小批次，例如三个合成用户共十条事件，再计算事件数和用户数：

```sql
SELECT
    event,
    count() AS event_count,
    uniqExact(distinct_id) AS exact_users
FROM sensors.event
WHERE event = 'integration_test'
  AND properties['validation_run'] = '2026-09-17-b'
GROUP BY event;
```

验收阶段使用精确函数更容易判断结果。生产环境是否换用其他聚合函数，应根据准确度、数据规模和成本明确决定，并写入指标定义。

## 5. 在 Superset 重现同一结果

先在 SQL Lab 执行已经验证的 SQL，确认与 ClickHouse 客户端结果一致，然后再保存数据集和图表。Superset 的数据库连接、数据集与图表工作流应参考 [Apache Superset 官方文档](https://superset.apache.org/docs/intro/)。

结果不一致时，依次检查：

- 虚拟数据集是否改写 SQL；
- 图表和看板过滤器；
- 时间字段、时间粒度和时区；
- 缓存是否仍保留旧结果；
- 行级权限是否改变可见数据；
- 用户去重字段和函数是否一致。

截图不能替代验收记录，因为截图通常不包含 SQL、过滤条件和数据刷新时间。应把验证 SQL 与指标定义一起版本化。

## 6. 故障路径也必须测试

至少覆盖重复请求、非法字段、数据库短暂不可用、接收服务重启和移动端延迟上报。团队需要明确系统是至多一次、至少一次，还是通过幂等键实现近似的有效一次。

如果相同请求可能重复写入，就必须在查询层或写入层提供明确去重规则；如果非法属性会被忽略，也必须能够从日志或错误记录中发现。

## 7. 迁移期用灰度和对账代替一次性切换

在客户端与基础设施允许时，使用双写、流量镜像或小比例灰度。按固定时间窗口比较事件总量、用户数、属性缺失率、属性类型、延迟、重复率和关键业务步骤。

新旧系统不一定天然完全一致。数据截止时间、迟到事件、身份合并、去重和过滤规则都可能造成合理差异。验收的目标是解释差异，而不是只让总数看起来相同。

## 上线检查表

- [ ] 唯一测试事件能够在原始表中准确定位；
- [ ] 身份关联符合书面定义；
- [ ] 客户端时间与接收时间可以区分；
- [ ] 代表性属性类型没有变化；
- [ ] 确定批次得到预期事件数和用户数；
- [ ] ClickHouse 与 Superset 查询结果一致；
- [ ] 时区、过滤器、缓存和权限已经记录；
- [ ] 重试、重复、非法载荷和服务重启已经测试；
- [ ] 回滚步骤和负责人明确；
- [ ] 生产备份和恢复流程经过演练。

## SensorFlow 在这套流程中的位置

[SensorFlow](https://github.com/data-analyze-bi/sensorFlow) 提供一条 Apache-2.0 开源实现：兼容的标准事件上报进入 Go 接收服务，写入 ClickHouse，再通过 Apache Superset 查询和展示。代码和部署文件公开，团队可以检查真实数据路径。

它适合愿意维护 Docker、ClickHouse 和 SQL 指标的工程团队，不等同于包含会话回放、实验、Feature Flag 和大量无代码分析流程的完整产品套件。SensorFlow 是独立项目，与神策数据不存在关联、背书或官方认证；具体 SDK 版本、插件、加密和批量上报方式必须逐项验证。

进一步的架构与检查项可查看 [ClickHouse + Superset 埋点分析指南](https://sensorflow.site/use-cases/clickhouse-superset-analytics)；已有神策 SDK 的团队可参考 [接收边界迁移指南](https://sensorflow.site/use-cases/sensors-sdk-to-clickhouse)。

可靠的埋点数据来自可追溯的验证链路，而不是一个绿色状态码。先证明一条事件正确，再证明一个已知批次正确，最后在受控流量中证明新旧链路的差异可以解释。
